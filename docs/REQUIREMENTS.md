# BRIDGE 要件定義書

## 1. 概要

### 1.1 背景と目的

レストランにおいて、客は注文・追加注文・会計依頼のたびに店員を探して手を挙げ、呼び止める必要があった。店員側も広いフロアで挙手を見落とし、対応漏れが発生していた。

BRIDGE は客のスマートフォンと店舗の管理画面を直結させ、以下を実現する。

- 客が店員を呼ばずに注文・呼び出し・会計依頼を行える
- 店員側の画面に依頼が即時表示され、対応するまで消えないため見落としが起きない
- 未提供の商品が一覧で把握でき、出し忘れを防げる

### 1.2 システム構成

| 名称 | 対象者 | アクセス方法 |
|---|---|---|
| **FRONT-system** | 客 | 各席に固定設置された QR コードを読み取る |
| **BACK-system** | 店員 | ID・パスワードでログイン |

両者は Supabase(データベース・リアルタイム配信)を介して連携する。

### 1.3 用語定義

| 用語 | 定義 |
|---|---|
| 席 (table) | 物理的なテーブル。固定の QR コードが1つ紐づく |
| 会計セッション (session) | 1組の来店から会計完了までの単位。複数回の注文を束ねる |
| 伝票 | 1セッションに属する全注文明細と合計金額 |
| 提供タイミング | 商品を出すタイミング。**食中** または **食後** |
| 呼び出し | 客から店員への通知。呼び鈴・食後提供の合図・会計依頼の3種 |

## 2. スコープ

### 2.1 対象範囲

- FRONT-system(注文用アプリ)の全機能
- BACK-system(従業員操作用管理パネル)の全機能
- 上記を支えるデータベース・認証・リアルタイム通知基盤

### 2.2 対象外(今回は実装しない)

明示的にスコープ外とし、必要になった時点で追加検討する。

| 項目 | 理由 |
|---|---|
| オンライン決済(クレジットカード決済等) | 会計は従来どおりレジで実施。BRIDGE は通知と伝票表示までを担う |
| キッチンプリンタ連携 | 専用機器と有料サービスが必要。画面での運用とする |
| POS レジ・会計システムとの連携 | 同上 |
| 売上分析・レポート機能 | 要件に含まれないため。データは蓄積されるので後から追加可能 |
| 予約管理・座席管理 | 要件に含まれない |
| 多言語対応 | 要件に含まれない。将来拡張として設計上は考慮する |

## 3. 機能要件

### 3.1 BACK-system(従業員操作用管理パネル)

#### 商品管理

| ID | 機能 | 内容 |
|---|---|---|
| BK-01 | 商品の追加 | 種類(カテゴリ)・提供パターン(即提供のみ / 食中・食後を選択可能)・価格・商品名を指定して登録する。さらに「オプションあり/なし」を選び、ありの場合はオプション名と追加料金を1つ以上登録できる(例: ごはん大盛+50円)。**ドリンクカテゴリの商品**では、これに加えてセット割引の名称と割引額を設定できる(例: セット割引 -100円。3.1.4 参照) |
| BK-02 | 商品の削除 | 商品をメニューから外す。**論理削除**とし、過去の伝票データは保持する(理由は 3.1.1 参照) |
| BK-03 | 商品の編集 | 商品名・価格・提供パターンの変更、提供可否(品切れ)の切り替え、オプションの追加・追加料金の変更・削除、およびドリンクのセット割引の設定・変更・解除を行う |
| BK-04 | カテゴリ管理 | カテゴリ(種類)の追加・並び替え |

##### 3.1.1 商品削除を論理削除とする理由

商品をデータベースから物理削除すると、その商品を含む過去の注文明細が参照先を失い、伝票の再表示や売上の集計ができなくなる。そのため以下の2段構えとする。

- 注文明細には**注文時点の商品名と価格をコピーして保存**する(以後メニュー側を変更しても過去の伝票は変わらない)
- 商品の削除は「メニューに表示しない」フラグを立てる論理削除とする

なお「今日は品切れ」の場合は削除ではなく **品切れフラグ**(BK-03)を使う。翌日ワンタッチで復活でき、誤って削除する事故も防げる。

##### 3.1.4 ドリンクのセット割引

ドリンク以外の商品と同じ来店(セッション)で1点でも注文していれば、対象ドリンクの単価が自動的に割引される機能。

- 割引を設定できるのは**ドリンクカテゴリの商品のみ**。名称(例: セット割引)と割引額を商品ごとに1つ持つ
- 判定範囲は**来店中(セッション全体)**。ドリンクだけを先に注文し、あとから他の商品を追加注文した場合でも、その時点以降に送信するドリンクの注文には割引が適用される。ただし**既に確定した過去の注文の金額は遡って変わらない**(注文時点の単価をそのままコピー保存する方式のため。3.1.1 と同じ考え方)
- お客様の操作は不要で、条件を満たした注文は自動的に割引価格になる

#### 注文・提供管理

| ID | 機能 | 内容 |
|---|---|---|
| BK-05 | 注文照会 | 席ごとの伝票データを閲覧する。注文された商品・数量・単価・合計金額・注文時刻を表示 |
| BK-06 | 提供状況の確認 | **まだ提供していない商品の一覧**を表示する。「食中」と「食後」を分けて表示する(理由は 3.1.2 参照) |
| BK-07 | 提供済みの記録 | 商品を出したらワンタッチで提供済みにする。**商品1点ごと**に管理する |
| BK-08 | 新規注文の即時通知 | 客が注文を送信した瞬間に画面に表示する。対応するまで消えない |

##### 3.1.2 提供状況を「食中」「食後」で分ける理由

食後のデザートやドリンクは、意図的に提供を保留している商品である。これを未提供一覧に混ぜて表示すると、本当に出し遅れている食中の商品が埋もれてしまう。そのため以下のように分けて表示する。

- **食中・未提供** … 今すぐ出すべきもの(遅延の警告対象)
- **食後・待機中** … 客からの合図(FR-06)を待っているもの

##### 3.1.3 提供状況を商品1点ごとに管理する理由

1回の注文に複数の商品が含まれる場合、料理は同時に出来上がらない。注文単位で「提供済み」を管理すると、5品中4品を出した状態を表現できず「まだ出していないものがないか」の把握という要件を満たせない。したがって商品1点ごとに提供済みを記録する。

#### 呼び出し・会計

| ID | 機能 | 内容 |
|---|---|---|
| BK-09 | 呼び出し通知の受信 | 客が呼び鈴を押した際に席番号とともに即時表示する。対応済みにするまで消えない |
| BK-10 | 食後提供合図の受信 | 客が食後商品の提供を求めた際に、該当する商品名とともに表示する |
| BK-11 | **会計通知の受信** | 客が会計ボタンを押した際に席番号と合計金額を即時表示する |
| BK-12 | 会計の完了処理 | レジでの精算後、会計を完了としてセッションを閉じる。以後その席は新しい客を受け入れる |

#### その他

| ID | 機能 | 内容 |
|---|---|---|
| BK-13 | 店員ログイン | ID・パスワードによる認証。未ログインでは一切の情報にアクセスできない |
| BK-14 | 席・QR コード管理 | 席の登録と、その席の QR コードの表示・印刷用出力 |

### 3.2 FRONT-system(注文用アプリ)

#### 注文

| ID | 機能 | 内容 |
|---|---|---|
| FR-01 | QR コードによる入店 | 各席に固定設置された QR コードを読み取ると、その席専用の注文画面が開く。**アプリのインストールもログインも不要** |
| FR-02 | メニュー表示 | Supabase から商品一覧を読み込み、カテゴリ別に表示する。品切れ商品は選択できない状態で表示する。オプションのある商品は、チェックボックスで追加料金を確認しながら選べる(例: ごはん大盛+50円)。セット割引のあるドリンクには、割引条件の案内を表示する |
| FR-03 | **提供タイミングの選択** | 店員が「食中・食後を選択可能」に設定した商品は、注文時に「食中」「食後」を選択する |
| FR-04 | 注文の送信 | 選択した商品をまとめて送信する。**追加注文も同じ操作**で行え、同一セッションに追加されていく |
| FR-05 | 注文内容の確認 | 自席のこれまでの注文内容と、各商品の提供状況を確認する |

#### 呼び出し

| ID | 機能 | 内容 |
|---|---|---|
| FR-06 | **呼び鈴** | 追加注文の相談や用事がある際に、ボタン1つで店員を呼ぶ |
| FR-07 | **食後商品提供の合図** | 食後に指定した商品を「今出してほしい」と伝える。保留中の食後商品がある場合のみボタンを表示する |

#### 会計

| ID | 機能 | 内容 |
|---|---|---|
| FR-08 | **会計依頼** | 会計ボタンを押すと店員に通知が飛ぶ |
| FR-09 | **デジタル伝票の表示** | 会計ボタンを押すと、**その席の未会計の全注文を1つにまとめた伝票**をスマートフォン上に表示する。商品名・数量・単価・小計・合計金額を含む |

## 4. データ設計

### 4.1 テーブル構成

```
tables(席) ──< sessions(会計セッション) ──< orders(注文) ──< order_items(注文明細)
                      │                                            │
                      └──< staff_calls(呼び出し)                    └── menu_items(商品) >── categories(カテゴリ)

staff_users(店員)
```

### 4.2 各テーブルの定義

#### tables(席)

| カラム | 型 | 説明 |
|---|---|---|
| id | uuid | 主キー |
| table_number | text | 席番号(例: `A-1`, `12`) |
| qr_token | text | QR コードに埋め込む固定の文字列。**推測不能なランダム値**とする |
| is_active | boolean | 使用中の席かどうか |

QR コードは席ごとに固定であり、更新されない(要件による)。席番号をそのまま URL に使うと他席になりすませるため、ランダムなトークンを用いる。

#### sessions(会計セッション)

| カラム | 型 | 説明 |
|---|---|---|
| id | uuid | 主キー |
| table_id | uuid | 席への参照 |
| status | text | `active`(利用中) / `checkout_requested`(会計依頼済み) / `closed`(会計完了) |
| opened_at | timestamptz | 最初の注文が入った時刻 |
| closed_at | timestamptz | 会計完了時刻 |

**1つの席に `active` なセッションは同時に1つだけ**存在する。最初の注文時に自動生成され、店員の会計完了操作(BK-12)で閉じる。「会計が行われていないその席番号の全注文」(FR-09)とは、この `active` / `checkout_requested` セッションに属する注文を指す。

#### categories(カテゴリ・種類)

| カラム | 型 | 説明 |
|---|---|---|
| id | uuid | 主キー |
| name | text | カテゴリ名(例: 定食、その他主食、デザート、ドリンク) |
| is_drink | boolean | ドリンクカテゴリか。true の場合のみ商品ごとにセット割引(3.1.4)を設定できる |
| sort_order | int | 表示順 |

#### menu_items(商品)

| カラム | 型 | 説明 |
|---|---|---|
| id | uuid | 主キー |
| category_id | uuid | カテゴリ(種類)への参照 |
| name | text | 商品名 |
| price | int | 価格(円・整数) |
| description | text | 説明(任意) |
| allows_timing_choice | boolean | **客が「食中/食後」を選べる商品か**。BK-01(追加時)・BK-03(編集時)で商品ごとに店員が設定する |
| combo_discount_name | text | セット割引の名称(例: セット割引)。ドリンクカテゴリの商品のみ設定可能。未設定なら null |
| combo_discount_amount | int | セット割引の金額(1点あたり・円)。0なら割引なし |
| is_available | boolean | 提供可否(品切れでないか) |
| is_deleted | boolean | 論理削除フラグ(BK-02) |
| sort_order | int | 表示順 |

#### menu_item_options(商品オプション)

| カラム | 型 | 説明 |
|---|---|---|
| id | uuid | 主キー |
| menu_item_id | uuid | 商品への参照 |
| name | text | オプション名(例: ごはん大盛) |
| extra_price | int | 追加料金(1点あたり・円) |
| is_deleted | boolean | 論理削除フラグ |
| sort_order | int | 表示順 |

商品ごとに0件以上持つ。ドリンクのように追加料金のオプションを持たない商品は0件のままにする。

#### orders(注文)

| カラム | 型 | 説明 |
|---|---|---|
| id | uuid | 主キー |
| session_id | uuid | セッションへの参照 |
| created_at | timestamptz | 注文時刻 |

1回の送信操作が1レコードになる。追加注文は同じセッションに新しい `orders` として積み上がる。

#### order_items(注文明細)

| カラム | 型 | 説明 |
|---|---|---|
| id | uuid | 主キー |
| order_id | uuid | 注文への参照 |
| menu_item_id | uuid | 商品への参照 |
| item_name | text | **注文時点の商品名のコピー** |
| unit_price | int | **注文時点の単価のコピー** |
| quantity | int | 数量 |
| serve_timing | text | `during`(食中) / `after`(食後) |
| status | text | `pending`(未提供) / `served`(提供済み) |
| served_at | timestamptz | 提供時刻 |
| category_is_drink | boolean | **注文時点でドリンクカテゴリだったかのコピー**。セット割引(3.1.4)の判定を、あとでカテゴリ構成が変わっても正しく再現するために保存する |

`unit_price` には、選んだオプションの追加料金を合算し、セット割引が適用できるドリンクなら割引額を差し引いた金額を入れる(基本価格のみではない)。こうすることで伝票合計・売上集計の計算式を変えずに済む。

#### order_item_options(選択されたオプション・適用された割引)

| カラム | 型 | 説明 |
|---|---|---|
| id | uuid | 主キー |
| order_item_id | uuid | 注文明細への参照 |
| option_name | text | **注文時点のオプション名(またはセット割引名)のコピー** |
| extra_price | int | **注文時点の追加料金のコピー**(1点あたり)。セット割引が適用された場合は負の値(例: -100)を入れる |

`order_items.unit_price` の内訳を表示するための明細。オプションの追加料金だけでなく、適用されたセット割引もここに記録する。後からオプションやセット割引の設定を変更・削除しても、過去の伝票の表示は変わらない。

#### staff_calls(呼び出し)

| カラム | 型 | 説明 |
|---|---|---|
| id | uuid | 主キー |
| session_id | uuid | セッションへの参照 |
| type | text | `bell`(呼び鈴) / `serve_after`(食後提供の合図) / `checkout`(会計依頼) |
| status | text | `open`(未対応) / `handled`(対応済み) |
| created_at | timestamptz | 発生時刻 |
| handled_at | timestamptz | 対応時刻 |
| handled_by | uuid | 対応した店員 |

3種の呼び出しを1テーブルで扱うことで、店員画面に**未対応の依頼が時系列で一覧表示**され、種類を問わず取りこぼしがなくなる。

#### staff_users(店員)

| カラム | 型 | 説明 |
|---|---|---|
| id | uuid | Supabase Auth のユーザー ID |
| display_name | text | 表示名 |
| role | text | `admin`(商品・席の管理が可能) / `staff`(注文対応のみ) |

## 5. 非機能要件

### 5.1 セキュリティ

| 項目 | 方針 |
|---|---|
| 客側の認証 | **認証なし**。QR トークンを知っていることが唯一の資格情報 |
| 客のデータアクセス | データベースへの直接アクセスは**全面的に禁止**する。注文・呼び出し・伝票取得はすべてサーバー側処理(Supabase Edge Functions)を経由し、そこで QR トークンを検証する |
| 客が読めるもの | メニュー(商品・カテゴリ)のみ。他席の注文・伝票は一切参照できない |
| 店員側の認証 | Supabase Auth によるメールアドレス+パスワード認証 |
| 権限制御 | 全テーブルで行レベルセキュリティ(RLS)を有効化し、データベース側で強制する |
| 秘密情報の管理 | `service_role` キー・DB パスワードはサーバー側にのみ配置。フロントエンドのコードには一切含めない |

##### 客側を「認証なし + サーバー側処理経由」とする理由

客ごとにアカウントを作る方式(匿名認証)も検討したが、以下の理由で採用しない。

- 来店のたびにユーザーレコードが際限なく増え、無料枠の消費とデータ肥大を招く
- 「伝票は席に属する」という店舗の実態と合わない。同じ席の複数人がそれぞれ QR を読んでも同じ伝票が見えるべきである
- アカウントと席を紐づける仕組みが追加で必要になり、構成が複雑になる

QR トークンを鍵として扱い、判断をサーバー側に集約するほうが単純かつ安全である。

### 5.2 性能・可用性

| 項目 | 目標 |
|---|---|
| 注文・呼び出しの店員画面への反映 | 3秒以内 |
| メニュー表示 | 2秒以内(3G 相当の回線を想定) |
| 同時利用 | 全席同時の注文操作に耐えること |
| 店員端末 | 同時に3台程度のログインを想定 |

### 5.3 対応環境

| 対象 | 環境 |
|---|---|
| FRONT-system | スマートフォンのブラウザ(iOS Safari / Android Chrome)。アプリのインストール不要 |
| BACK-system | タブレットまたは PC のブラウザ。画面は縦横どちらでも操作できること |

### 5.4 運用上の要件

| ID | 内容 |
|---|---|
| OP-01 | 会計完了操作(BK-12)を忘れると次の客の注文が前の客の伝票に混ざる。**最終注文から一定時間が経過したセッションを自動的に閉じる**安全装置を設ける |
| OP-02 | 店内 Wi-Fi またはモバイル回線で動作すること。特定のネットワークに依存しない |
| OP-03 | QR コードは印刷して各席に固定設置する。BACK-system から印刷用に出力できる(BK-14) |

## 6. 利用ツールと無料枠での運用

### 6.1 使用するサービス(3つのみ)

| サービス | 用途 | プラン |
|---|---|---|
| **GitHub** | ソースコード管理・自動テスト | 無料(パブリックリポジトリ) |
| **Supabase** | データベース・店員認証・リアルタイム通知・サーバー側処理 | 無料プラン |
| **Vercel** | FRONT-system と BACK-system の配信 | 無料プラン(Hobby) |

QR コードの生成はアプリ内で行い、外部サービスは使用しない。これ以外に必要なサービスはない。

### 6.2 無料枠の上限と想定使用量

30席・1日100組の利用を想定した試算。

| 項目 | 無料枠の上限 | 想定使用量 | 判定 |
|---|---|---|---|
| データベース容量 | 500 MB | 年間約 40 万行、数十 MB | ◎ 数年間は余裕 |
| リアルタイム同時接続 | 200 | 店員端末 3 台程度 | ◎ |
| リアルタイム通信量 | 200 万メッセージ/月 | 数万メッセージ/月 | ◎ |
| サーバー側処理の実行回数 | 50 万回/月 | 約 1.5 万回/月 | ◎ |
| 転送量(Supabase) | 5 GB/月 | 6.2 参照 | △ **要注意** |
| 転送量(Vercel) | 100 GB/月 | 数 GB/月 | ◎ |

### 6.3 無料枠を守るための設計判断

#### 商品画像は初期リリースでは扱わない

要件では商品の登録項目として画像が挙げられていない。加えて画像を Supabase に置くと、客がメニューを開くたびに転送量を消費し、**月 5 GB の無料枠を超過する可能性が最も高い項目**となる(1組あたり2MB×3,000組で 6 GB)。

したがって初期リリースは**商品名・価格・説明のテキストのみ**とする。画像が必要になった場合は、Supabase ではなく Vercel 側(無料枠 100 GB)から配信する方式で追加する。

#### プロジェクトの一時停止に注意

Supabase の無料プランは **7 日間アクセスがないとプロジェクトが自動停止**する。日々営業していれば問題ないが、開発完了から開店までに間が空く場合や長期休業の際は、ダッシュボードから復帰操作が必要になる。

#### Vercel の商用利用について

Vercel の無料プラン(Hobby)は**非商用利用に限定**されている。開発・試験運用の段階では問題ないが、実店舗の営業で使用する段階では Pro プラン(月額 20 ドル)への変更が必要となる。無料での運用を継続したい場合は、Cloudflare Pages(無料・商用利用可)への移行で対応できる。**本システムは静的ファイルとして配信されるため、移行はビルド設定の変更のみで完了し、コードの修正は発生しない。**

## 7. 主要な業務フロー

### 7.1 来店から会計まで

```
1. 客が着席し、卓上の QR コードを読み取る
      ↓
2. その席のメニュー画面が開く(インストール・ログイン不要)
      ↓
3. 商品を選択。デザート・ドリンクは「食中」「食後」を選ぶ
      ↓
4. 注文を送信
      ├─→ 会計セッションが自動で開始(初回のみ)
      └─→ BACK-system に即時表示(BK-08)
      ↓
5. 店員が調理・提供し、出した商品を提供済みにする(BK-07)
      ↓
6. 追加注文があれば 3〜5 を繰り返す(同じセッションに積み上がる)
      ↓
7. 食事が済んだら「食後の商品を出してください」を押す(FR-07)
      └─→ BACK-system に該当商品名とともに表示(BK-10)
      ↓
8. 客が会計ボタンを押す(FR-08)
      ├─→ BACK-system に席番号と合計金額を表示(BK-11)
      └─→ 客のスマートフォンにデジタル伝票を表示(FR-09)
      ↓
9. 客がレジで精算。店員が会計完了を操作(BK-12)
      └─→ セッションが閉じ、その席は次の客を受け入れる
```

### 7.2 呼び鈴

```
客が呼び鈴を押す(FR-06)
   ↓
BACK-system の未対応リストに席番号が表示される(BK-09)
   ↓ ※対応済みにするまで消えない
店員が席へ向かい、対応後に「対応済み」を押す
```
